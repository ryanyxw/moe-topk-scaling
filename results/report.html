Final report · Mon 26 Oct 2026, 10:00 UTC

Scaling active experts in a Nemotron-3-Nano-style MoE

8× H100 node (GPU 1 excluded) · Megatron-Bridge · FineWeb-Edu 350BT

Goal

Find how loss scales with the number of active experts (top-k) and the number of training tokens, at a fixed total parameter count. Fit compute-optimal isoFLOP curves at three budgets over about 3 days, then spend about 4 days on one larger run (~4.5e20 FLOPs, 9× beyond the largest sweep budget) to check whether the fitted law extrapolates.

Headline result

The fitted law predicted the 4.5e20 run to within 0.013

The final run (top-k 12, 134.3B tokens, 4.5e20 FLOPs) finished at validation loss 2.2405. The C1–C4 joint fit, made before the run started, predicted 2.253. The run came in 0.013 (0.6%) better than predicted, 4.5× beyond the largest sweep budget.

The miss is in the same direction as the fit's own backtest. Fitting only C1–C3 and predicting C4 also came out pessimistic: 2.369 predicted against 2.362 measured for top-k 8, a gap of 0.007 at a 2× extrapolation. The fitted floor E drifts down as larger budgets are added, so the fit slightly underestimates how much more data helps. Refitting with the final point included changes the optimum very little: k* = 10.8 at 4.5e20 (was 11.1) and 12.5 at 1e21.

Downstream: across 21 checkpoints and 10 NeMo Evaluator benchmarks, average accuracy tracks validation loss (r = −0.99), and the loss-optimal top-k is also the accuracy-optimal one at every budget. The final run averages 60.0% on the 8 informative tasks (HellaSwag 61.1). Details in Downstream evaluations below.

Plan

Each run is identified by its compute budget and top-k. Within a budget, changing top-k changes FLOPs per token, so the run sees a different number of tokens. Each larger budget resumes from the cooldown-start checkpoint of the same top-k at the previous budget, so the constant-LR phase is never trained twice.

Top-k 1 (2.757) beats top-k 2 (2.827) by 0.07, more than twice the noise level, and the same ordering appeared at C0. The likely cause is the router: at top-k 1 the expert weight is the raw sigmoid score times 2.5, a gate scale the model can learn. At top-k 2 and above, the weights are normalized to sum to 2.5. So top-k 1 is effectively a different architecture.

Downstream evaluations

21 of 21 models finished (updated Mon 26 Oct, 09:58 UTC). Each checkpoint was converted to Hugging Face format with Megatron-Bridge, served with vLLM 0.12 on one GPU, and scored with the NeMo Evaluator launcher (0.2.6) using NVIDIA's lm-evaluation-harness container (26.03). All tasks are multiple-choice or completion tasks scored by answer log-likelihood, which works for base models of this size.

Conversion check: on the same validation text, vLLM's per-token losses match the Megatron checkpoint to within 0.003 at every position, and every served model's validation loss sits a consistent 0.01–0.02 below the Megatron number (different windows). The newer Hugging Face transformers implementation does not match (≈0.14 per-token gap), so it is not used anywhere.

Scores are accuracy in %: length-normalized (acc_norm) for HellaSwag, ARC, PIQA, OBQA and SciQ, plain accuracy for Winogrande, LAMBADA and MMLU. Shots: HellaSwag 10, Winogrande 5, MMLU 5, ARC-C 25-shot variant 25, others 0. Chance: 25% (50% for PIQA and Winogrande). Avg (8) averages the eight tasks that are above chance. MMLU and the 25-shot ARC-C (which asks for an answer letter) stay at chance for every model, as expected at this scale. Error bars (1 s.e.): about ±0.5 for HellaSwag, ±1.0–1.4 for ARC, PIQA and Winogrande, ±2.2 for OBQA.

Result: downstream accuracy follows validation loss

  • Loss predicts accuracy. Across the 17 cooled-down models, the 8-task average correlates with validation loss at r = −0.99 (HellaSwag −0.996, PIQA −0.993, LAMBADA −0.991; Winogrande is the noisiest at −0.84). Top-k changes neither the slope nor the offset: models with different top-k but the same loss score the same.
  • The loss-optimal top-k is also the accuracy-optimal top-k. At all four budgets, top-k 8 has both the lowest loss and the highest 8-task average (C1 45.5, C2 49.4, C3 53.6, C4 56.1). The margins over the runner-up are 0.2–0.9 points, about the size of the noise, so this agrees with the loss ranking but doesn't independently confirm it.
  • The final run (top-k 12, 4.5e20) averages 60.0, up 3.9 points on the best C4 model: HellaSwag 61.1, ARC-E 68.7, SciQ 86.9, LAMBADA 46.4.
  • The cooldown buys about 3.6 points. The final run's checkpoint at step 104k (cooldown start, loss 2.375) averages 56.4; after the cooldown it averages 60.0. Pre-cooldown checkpoints fall on the same loss–accuracy line as cooled-down models (step 26k: loss 2.458, avg 53.6; C3 top-k 8: 2.439, 53.6), so what matters is the loss reached, not how it was reached.
  • Not informative at this scale: MMLU (24–26% for every model) and the letter-answer 25-shot ARC-C (24–28%) stay at chance; the 0-shot ARC-C shows the trend instead (25 → 40).

Noise estimate

Top-k 4, LR 3e-3 at C0: 2 GPUs, seed A: 3.196. 1 GPU, seed A: 3.213. 1 GPU, seed B: 3.231. So changing the seed moves the result by about 0.018, and running on 1 GPU adds about 0.017. I treat ±0.02 as the error bar on small-budget points; single-GPU points are kept out of the fits.

Analysis plan

  • Per budget: fit a parabola of loss against log tokens (equivalently, top-k) to locate the optimal top-k and token count.
  • Across budgets: fit power laws for the optimal top-k and optimal token count as functions of compute, and extrapolate them to ~4.5e20.
  • Joint fit: fit L(top-k, D) to all cooldown points, about 20× in tokens. That uses many more points than the per-budget parabolas, so it's less sensitive to noise.
  • Final run: use the fitted optimal top-k with total experts fixed, then compare its loss to the predicted value.

Issues found and fixed

  • Silent from-scratch training: a relative checkpoint path made a resumed run start from step 1. Runs now refuse to start unless a real checkpoint exists.
  • Resume warmup mismatch: top-k 16 at C1 has fewer than 2000 steps, so its warmup is 195, not 200. Extensions now read the warmup from the parent run's log.
  • CPU contention: tokenization was slowing training; the two now run on separate cores.
  • Scheduler clash: two jobs once landed on the same GPUs. The scheduler now uses only GPUs with no memory in use, and re-adopts running jobs after a restart.
  • Idle GPUs: two pairs sat idle for 1.3 hours between stages. The whole sweep is now queued up front, with dependencies.
  • Changing the GPU count on resume: a checkpoint can't be loaded with a different expert split (2 GPUs → 1 fails with KeyError: 'optimizer'). Keeping the 2-GPU expert split and changing only data parallelism (2 → 4 GPUs) works, and that's how C3 top-k 8 runs.
  • Training data ran out at C4 (19 Oct): every run used the same 40 shards (~3.68M sequences, ~30B tokens), but C4 top-k 4 and 8 need 44.6B and 35.8B tokens. Top-k 4 crashed at step 28770 with StopIteration. A new option resumes from the step-28500 checkpoint onto fresh shards 40–79, with the data sampler offset so no sequence is repeated (about 0.3B unused tokens of the old set are skipped). It was tested on GPU 7, then top-k 4 passed the old limit on real data at 11:58 UTC. Top-k 8 hit the same limit at 19:48 UTC; its automatic retry switched the same way and passed the old limit at 20:20. Top-k 16 needs only 25.6B tokens and is unaffected. Cost: about 50 minutes of top-k 4 compute.
  • Slow 6-GPU setup (20 Oct): the first final-run test reached only 150–195 TF/s per GPU. Cause: the job was confined to node-0 CPU cores (a leftover from running tokenization alongside training), while GPUs 4–6 sit on node 1. With all CPUs it runs at about 230 TF/s per GPU, faster than the 2-GPU runs.
  • Batch-size bug in the step count (20 Oct): steps were computed from a hardcoded 128-sequence batch, so with 126 the final run would have trained 1.6% past its budget. Fixed before launch; scaling-law runs (all 128) were unaffected.
  • Downstream-eval setup (26 Oct): (1) the newer Hugging Face transformers NemotronH code gives per-token log-probs about 0.14 off the Megatron model, while vLLM matches to 0.003, so evals use vLLM only; (2) the NeMo Evaluator launcher returns as soon as it submits, so the first attempt shut each server down too early; (3) with host networking, the evaluators' local proxies collided on ports (failures only: a request to the wrong server is rejected by model name); (4) anonymous Hugging Face downloads hit rate limits (HTTP 429) on MMLU's 57 subsets. Fixes: wait for each job's exit, per-container networks, a local tokenizer and shared dataset cache, and per-task retries.
  • Disk leak: crash-recovery checkpoints (88 GB per run) weren't being deleted, because the container writes them as root. Cleanup now uses sudo.

Caveats

  • At top-k 1 the router doesn't normalize its weights, and C1 confirms it behaves differently (see above), so the fits use top-k ≥ 2.
  • The final run differs slightly from the sweep: 126 instead of 128 sequences per step, 6 GPUs, and data drawn from all 471 shards rather than the first 40–80. None of these should move the loss by more than the ~0.005 eval noise, but they are not zero.
  • The router scaling factor is kept at Nano's 2.5 for every top-k.
  • The fitted budgets (C1–C4) span 12.5× in compute, and the final run is a single 4.5× extrapolation at a single top-k. It tests the predicted loss, not the location of k*: top-k 8 and 16 were predicted to be only 0.003 worse, which is below what one run can resolve.
  • Checkpoints and data live on local NVMe. They survive reboots, but are lost if the VM is stopped or moved for host maintenance.
